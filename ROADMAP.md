Единый план развития и приёмки проекта. Источник истины — этот файл в Git; текущую реализацию и правила безопасности см. в README.ru.md, docs/architecture.md, docs/MAINTAINING.md и AGENTS.md.

Команды «продолжаем по роудмапу» достаточно, чтобы в новом чате открыть этот файл и приступить к следующему доступному пункту с проверками через MCPshka.

## P06 — 1.4.0: собственная карточка устройства и управление в Home Assistant

Согласовано владельцем 27.11.2026. LocalTuya остаётся единственным транспортом. HA 2026.8+ запрещает присоединение второго config entry к одному DeviceEntry (https://contributors.home-assistant.io/blog/2026/07/21/device-registry-single-config-entry/). Поэтому Venta получает собственное логическое устройство с явным указанием транспорта, а не переносит/присваивает существующее устройство LocalTuya. Исходные entity IDs, автоматизации, история и HomeKit/Yaha exports остаются неизменными; новые интерфейсные сущности не экспортируются автоматически. YAML-установка сохраняется; добавление UI-карточки через существующий согласованный миграционный путь, без автоматического удаления YAML или restart.

## Общие инварианты — действуют для каждого пункта

- Не менять integration domain venta_homekit_native, HomeKit bridge identity, pairing, Home Assistant entity IDs, локальные ключи Tuya и рабочие DP mappings без отдельного плана миграции и подтверждения владельца.
- Не форкать LocalTuya без доказанной необходимости. Не создавать параллельное локальное подключение к реальному устройству.
- Секреты, реальные IP/MAC, HomeKit .storage, приватные конфигурации, ключи и облачные токены не помещать в публичные репозитории и CI artifacts.
- Перед изменениями live HA сохранять резервную копию, проверять конфигурацию и путь отката; сервисные reset и физические команды только с разрешения пользователя.
- Источником проекта является локальный репозиторий H96; GitHub — основная Marketplace-площадка, GitVerse — публичное зеркало и дополнительный CI. Оба удалённых источника в конце выпуска проверять по содержимому.
- Различать: код написан → тесты PASS → CI PASS → опубликовано → установлено → подтверждено на устройстве. Пункты [x] только после полного Exit.
- При изменении HomeKit runtime, LocalTuya DP или migration проводить изолированную приёмку перед live HA. Не принимать зелёный CI как подтверждение реального устройства.

## Протокол ежедневного продолжения

1. На сообщение владельца «продолжаем по роудмапу» прочитать актуальный ROADMAP.md и AGENTS.md из проекта, а не полагаться на текст предыдущего чата.
2. MCPshka: mcpshka_guide topic=rules и roadmap, project_context, roadmap_next, Git status/diff, активные jobs/leases/deploy/checkpoints, последние CI/логи. Проверить, что нет другого writer или UNKNOWN job.
3. Взять первый приоритетный незакрытый пункт с реальным Exit. Выполнить код и тесты нативными средствами MCPshka; тяжёлые тесты — через разрешённые runner/CI, не через произвольный shell H96.
4. Сверить корректность commit SHA/tree, GitHub CI, GitVerse CI (через provider query при расхождении агрегированного forge_ci), затем installation/acceptance только там, где это требуется Exit и разрешено политикой.
5. Записать доказательства (commit, job/run ID, проверенный статус), обновить чекбоксы штатным roadmap_close при прохождении phase_gate; при HOLD указать конкретный blocker и взять независимый пункт.
6. В конце дать краткий отчёт: DONE / IN PROGRESS / BLOCKED, какие ID закрыты, что изменилось, результаты тестов, синхронизация зеркал, следующий пункт. Освободить только собственный подтверждённо idle lease.
7. Работа происходит в текущем вызове чата. Без специально зарегистрированной автоматизации новые задачи в фоне не выполняются. Следующее сообщение владельца запускает новый цикл.

## Риски и внешние зависимости

- Внутренние HomeKit/PyHAP API не являются стабильным публичным контрактом; совместимость каждой версии HA требует теста.
- HACS/Marketplace acceptance не гарантирован: в ранних релизах возможна установка как custom repository, без общего каталога.
- Поддержка других Venta и работа без LocalTuya — только после реальных проб и исследования протокола.
- Отдельная известная проблема MCPshka: forge_ci status может показывать RUNNING для terminal GitVerse run. При проверке использовать git_provider_query ci_runs; проблему нельзя приписывать исходникам Venta без доказательств.
